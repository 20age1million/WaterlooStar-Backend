---

## Purpose / Goal

Make `GET /listings` answer real questions: text search, the filters the housing
hub's rail offers, and the sorts its dropdown names — so the frontend can stop
filtering a page of results in the browser.

---

## Problem Statement / Motivation

The hub's filter rail is the product's stated difference from a classifieds
board: "rent, dates, distance, bedrooms and utilities are structured fields."
Phase 2 made that true in the database. The endpoint that serves it still
returns everything published, newest first, and the frontend filters whatever
page it happens to have — so a filter can only ever narrow the current 24 rows,
the result count is wrong, and a search cannot be shared.

---

## Proposed Solution / Design

One endpoint grows query parameters. Everything is optional, everything composes,
and the SQL is generated by sqlc from a single query using the standard
`WHERE (@param::type IS NULL OR column = @param)` shape so one prepared statement
serves every combination.

Full-text search uses a generated `tsvector` column over title, body,
neighbourhood and address line, with a GIN index — not `ILIKE`, which cannot use
an index and would match inside words.

### Key Components

- **`migrations/000004_listing_search.*`**: the `search` generated column, its GIN
  index, and btree indexes for the sortable columns.
- **`internal/db/queries/listings.sql`**: the filtered list and its matching count.
- **`internal/httpapi/listings.go`**: parameter parsing, validation, clamping.
- **`api/openapi.yaml`**: every parameter documented, with the enums the frontend
  already uses.

### Parameters

| Parameter | Meaning |
|---|---|
| `q` | Full-text search |
| `start_after`, `end_before` | Term window; the rail's presets map onto these |
| `price_min_cents`, `price_max_cents` | Monthly rent |
| `distance_max_m` | Straight-line metres to campus |
| `bedrooms_min` | 1, 2, 3+ |
| `furnished`, `parking`, `pets`, `laundry` | Amenities |
| `utilities` | Repeatable; a listing must include all requested |
| `verified_only` | Only listings whose owner is verified |
| `sort` | `match`, `new`, `priceAsc`, `priceDesc`, `distance` |
| `page`, `per_page` | Unchanged from Phase 2 |

## Trade-offs / Alternatives Considered

- **`tsvector` over `ILIKE`** — chosen. Indexed, word-aware, and ranks. `ILIKE
  '%term%'` cannot use an index and matches inside words.
- **A generated column over a trigger-maintained one** — chosen. PostgreSQL keeps
  it in step automatically; there is no trigger to forget.
- **One composable query over query building in Go** — chosen. sqlc generates it,
  so it stays type-checked, and there is no string concatenation near user input.
- **`distance_max_m` over true radius search** — forced. See Constraints.
- **Facet counts deferred** — the roadmap lists them here, but the counts the
  design shows ("Jan – Apr: 227") are home-page statistics, which the roadmap
  itself puts in Phase 12. This feature returns the matching total, which is what
  the results header needs. Deliberate reduction in scope.

---

## Constraints

- **No geocoding provider is chosen, so `lat`/`lng` are null on every row.** True
  radius-from-a-point search is impossible and belongs with the map in Phase 8.
  `distance_m` is populated and serves the rail's "Under 1 / 2 / 5 km" radios
  exactly, so the distance filter is a maximum against that column.
- **`sort=match` is accepted but orders by newest.** Real match scoring compares a
  listing against the viewer's own housing request, which does not exist until
  Phase 5, and is scored in Phase 8. Accepting the value now keeps the contract
  stable *(the frontend's `SortKey` already names it, per `WaterlooStar-Frontend/README.md`)*.
- The vocabulary rule stands: nothing named `renter` or `rentee`.
- Only published listings are ever returned, and that filter stays in the SQL.

## Success Criteria / Definition of Done

- Every parameter above filters, alone and in combination.
- `q` matches title, body, neighbourhood and address, and uses the index.
- Each sort orders correctly; `distance` puts listings with no distance last.
- The total reflects the filter, not the table.
- Unknown or malformed parameters answer with the standard error envelope.
- `go build`, `go vet`, `go test` pass; generators idempotent.

## Implementation Notes

**Key files changed:**

- `migrations/000004_listing_search.*` — generated `search` tsvector (weighted:
  title A, neighbourhood/address B, body C), GIN index, and partial btree indexes
  on price, distance and dates scoped to `status = 'published'`.
- `internal/db/queries/listings.sql` — `ListListings` and `CountListings`
  replace the unfiltered pair. Every filter is `sqlc.narg(...) IS NULL OR ...`,
  so one prepared statement serves every combination.
- `internal/httpapi/listings.go` — `filtersFrom` parses and validates; a
  `listingFilters` wrapper hands the same set to both list and count.
- `internal/httpapi/discovery_test.go` — 10 tests.
- `internal/httpapi/fake_querier_test.go` — the fake mirrors the new WHERE clause
  faithfully, so a handler test cannot pass against behaviour PostgreSQL rejects.

**Divergences from plan:** none. The two constraints named in the spec held:
`distance_max_m` against the populated column rather than radius search, and
`sort=match` accepted but ordering by newest.

**Decisions worth recording:**

- **A listing with no recorded distance is excluded when `distance_max_m` is
  set.** "Within 2 km" cannot honestly include "distance unknown". Tested.
- **`utilities` is conjunctive** — `@>` containment, so asking for internet and
  gas means a listing must include both. Tested, because "either" would be the
  easy mistake.
- **`verified_only=false` is not a filter for unverified listings**; it simply
  does not filter. Tested.
- **Whitespace-only `q` is no search**, not a search for the empty string.

**Verification run:**

- `go build`, `go vet`, `go test ./...` pass; generators idempotent.
- Migration up, down-one, up — clean.
- Against the six seeded listings: `q=basement` → 1; `q=quiet` → 3;
  `price_max_cents=80000` → 2; `distance_max_m=1000` → 3;
  `utilities=internet&utilities=gas` → 1; `furnished=true&pets=true` → 0;
  `sort=priceAsc` leads with the $700 room; `sort=distance` leads with the 500 m
  one; the Winter window → 4.
- Impossible ranges (max below min, end before start) → 400 in the standard envelope.
