## Purpose / Goal

Stand up the WaterlooStar API from an empty repository to a service that authenticates
verified University of Waterloo students and serves housing listings from PostgreSQL,
under a spec-first OpenAPI contract that the frontend generates its types from.

---

## Problem Statement / Motivation

The product exists only as a frontend prototype. Its three screens are a complete brief —
a two-sided housing marketplace gated on `uwaterloo.ca` verification — but every value on
them is a hard-coded constant in `src/data/housing.ts`. There is no server, no schema, and
no contract.

This feature builds the three layers everything else depends on: a running service with a
reviewable schema, an identity system, and the first read endpoints. Until they exist no
other feature in the roadmap can start — every one of them needs to know who is asking and
needs somewhere to persist what they write.

---

## Proposed Solution / Design

A Go service using gin, talking to PostgreSQL through pgx with queries generated by sqlc.
Schema is owned by versioned `golang-migrate` files, which sqlc also reads to derive its
types — so the migrations are the single source of schema truth.

The HTTP contract is **spec-first**: `api/openapi.yaml` is hand-written and authoritative.
`oapi-codegen` generates gin server interfaces from it, so a handler that drifts from the
contract fails to compile. The frontend repository generates its TypeScript types from the
same file.

Authentication is a JWT delivered in an httpOnly, SameSite cookie rather than a bearer
token, so the Next.js frontend can read it during server rendering and keep listing pages
server-rendered. Because the credential is a cookie, mutating routes are protected by a
double-submit CSRF token.

### Key Components

- **`cmd/api`**: process entry point — config load, pool open, router build, graceful shutdown.
- **`api/openapi.yaml`**: the contract. Edited before any handler that serves a new shape.
- **`internal/config`**: environment binding and validation; fails fast on a missing DSN.
- **`internal/db`**: pgx pool, sqlc-generated queries, and the `.sql` sources they come from.
- **`internal/httpapi`**: gin router, generated server interfaces, handler implementations.
- **`internal/middleware`**: request logging, CORS, recovery, `RequireAuth`, `RequireVerified`, CSRF.
- **`internal/auth`**: password hashing, token mint and verify, cookie shaping.
- **`internal/email`**: a `Sender` interface with a log-only implementation; provider deferred.
- **`migrations/`**: `golang-migrate` up/down pairs, the schema source of truth.

### Data / Control Flow

- A request enters gin and passes recovery, then request logging, then CORS, then any
  route-specific auth middleware.
- `RequireAuth` reads the session cookie, verifies the JWT signature and expiry, and puts the
  user id and verification state on the request context. `RequireVerified` additionally
  rejects unverified accounts.
- Handlers implement the generated server interface, call sqlc query methods, and map rows to
  generated response types.
- Every error leaves the service through one envelope shape defined in the OpenAPI components,
  so the frontend has exactly one error contract to handle.

## Trade-offs / Alternatives Considered

- **pgx + sqlc over GORM** — chosen. Generated, compile-checked queries and predictable SQL,
  at the cost of more code for simple CRUD. The prototype's existing GORM models are being
  discarded along with the rest of the old backend.
- **Spec-first over code-first OpenAPI** — chosen. One authoritative `openapi.yaml` means a
  contract change breaks compilation on whichever side has not caught up. Requires the
  discipline of editing the yaml before the handler.
- **httpOnly cookie over bearer token** — chosen so Next.js server components can fetch
  authenticated data during server rendering. Costs a CSRF mechanism a bearer token would not need.
- **golang-migrate over goose** — chosen because sqlc reads golang-migrate files natively to
  derive its schema, keeping one source of truth. goose's Go-code migrations would help with
  later data backfills; revisit if that need arrives.
- **UUID over bigint keys** — decided by the developer. Avoids leaking record counts in public
  listing URLs and makes merging records across environments safe. Costs index size.
- **Fresh start over porting `WaterlooStar-Backend`** — decided by the developer. The old models
  contradicted the SQL dump on key types and assumed GORM; little would have survived the rewrite.

## Assumptions

- Every user has exactly one `uwaterloo.ca` address and that address is a durable identity.
  Alumni losing address access is out of scope for this feature.
- PostgreSQL 18's built-in `gen_random_uuid()` is available, so no `pgcrypto` extension is needed.
- Listing photographs do not exist yet; the schema carries a photo table but Phase 2 seeds no rows.
- The frontend and API run on different origins in development, so CORS with credentials is required.

---

## Constraints

- The user-facing vocabulary is "Housing Available" and "Looking for Housing". The internal terms
  *renter* and *rentee* must never appear in any API path, field name or response body
  *(per `Waterloostar-web/README.md`)*.
- `SortKey` values already defined in the frontend — `match`, `new`, `priceAsc`, `priceDesc`,
  `distance` — are the intended server-side sort parameter names
  *(per `Waterloostar-web/README.md`)*.
- Street address is **public by default** for this feature. The design implies a private exact
  address revealed after contact; that decision is deliberately deferred and the schema must not
  make it expensive to add later.
- No email, image-hosting or map provider is selected. Anything needing one uses a placeholder
  implementation behind an interface.
- Local only: no remote is configured and nothing is pushed.

## Success Criteria / Definition of Done

- `docker compose up`, then `migrate up`, then `go run ./cmd/api` yields a service answering
  `/healthz` with a real database round-trip.
- A `uwaterloo.ca` address can register, be verified via a token, log in and reach an
  authenticated endpoint; a non-UW address is rejected at registration.
- `GET /listings` and `GET /listings/{id}` return seeded rows with structured fields, and an
  unknown id returns the standard 404 envelope.
- `api/openapi.yaml` describes every endpoint served, and the generated server interface
  compiles against the handlers.
- `go build ./...` and `go test ./...` pass.
- All phase checklists completed and verified.
